# 1단계-03 벙 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 운영진이 벙을 개설·수정·취소·복제하고, 동호회원이 신청·대기·취소하며, 끝난 벙의 참석을 자동 기록하고 운영진이 보정하는 흐름과 블랙리스트(늦은 취소·노쇼)를 API로 완성한다.

**Architecture:** 새 도메인 패키지 `meetup`(벙·신청), `attendance`(참석 기록·보정·자동 기록 작업), `penalty`(블랙리스트)를 만든다. 신청·참석·블랙리스트는 앱 계정이 아니라 **명부(`roster_members`)** 에 붙는다. 신청자의 명부 항목은 계획 2의 `RosterMemberRepository.findByUserId`로 찾는다. 정원 판정은 벙 행을 `PESSIMISTIC_WRITE`로 잠근 뒤 확정자 수를 센다. 대기자 승격은 `WaitlistPromoter` 한 곳에서만 한다. 푸시 알림은 계획 4에서 붙이고, 이 계획은 이벤트만 발행한다.

**Tech Stack:** 계획 1·2와 같음 (Spring Boot 4.1.2, Java 17, JPA, Flyway, H2 MySQL 모드/MySQL 8.4). 새 의존성 없음. 자동 참석 기록은 Spring `@Scheduled`.

**Spec:** `docs/architecture.md` 8장 "벙" 전체, 6장 역할 표, 9장 벙·운영진 화면 목록, 10장 `meetups`·`meetup_applications`·`attendances`·`penalties`. 규약은 `.claude/rules/api.md`, `.claude/rules/testing.md`, `api-conventions` 스킬. 앞 계획: `docs/superpowers/plans/2026-11-23-phase1-01-api-foundation-auth.md` (1단계 전체 계획 순서), `docs/superpowers/plans/2026-11-24-phase1-02-roster-membership.md`.

## Global Constraints

- 계획 1·2의 Global Constraints를 그대로 따른다 (패키지 구조, 응답 래퍼, record DTO, Lombok 제한, 생성자 주입, `@Transactional(readOnly = true)`, `Clock` 주입, 한국어 테스트 이름, AssertJ, `@ManyToOne(fetch = LAZY)`, 상태 변경은 엔티티 메서드로만, `...ForUpdate`는 `@Lock(PESSIMISTIC_WRITE)` + `@Query`).
- 시각: 저장은 UTC `Instant`. 요청 DTO의 시각 필드는 `OffsetDateTime`(오프셋 필수)으로 받아 `toInstant()`로 바꾸고, 응답은 기존 DTO처럼 `Instant`. 날짜 경계(목록 기간, 최근 3개월)는 `Asia/Seoul` 기준.
- 권한: 벙 조회·신청·취소·내 블랙리스트는 `@RequireRole(Role.MEMBER)` (ADMIN 포함), 그 밖의 이 계획 API는 `@RequireRole(Role.ADMIN)`.
- 신청 주체는 명부 항목이다. 호출자에게 연결된 명부가 없으면(DB에서 지정한 ADMIN 등) 신청·취소는 403 `MEETUP_ROSTER_REQUIRED`, 조회는 `my`를 `null`로 준다.
- 잠금 순서: **사용자 → 벙(`meetups`) → 신청(`meetup_applications`)·참석(`attendances`)·블랙리스트(`penalties`) → 동호회원 신청 → 명부**. 신청·취소·내보내기·정원 변경·벙 취소·자동 기록은 모두 벙 행을 먼저 잠근다.
- 신청·취소 마감은 시작 시각이다. `now >= startsAt`이면 409 `MEETUP_ALREADY_STARTED` (정확히 시작 시각도 마감).
- 늦은 취소: `deadline = startsAt - lateCancelHours`. 확정자가 본인 취소할 때 `now >= deadline` **이고** `confirmedAt < deadline`이면 `lateCancel = true`. 대기자 취소, 운영진 내보내기, 탈퇴 자동 취소는 항상 `false`. 블랙리스트는 자동으로 매기지 않는다.
- 확정 순서는 `confirmedAt, id` 오름차순, 대기 순번은 `appliedAt, id` 오름차순(1부터).
- 정원을 줄여도 확정자를 내리지 않는다. 승격은 `confirmedCount < capacity`인 동안만 한다.
- 블랙리스트 "최근 3개월"은 기록이 연결된 **벙의 `startsAt`** 이 `now`(서울)에서 3개월 전 같은 시각 이후인 활성(`revokedAt == null`) 기록 수다. `created_at`(감사용)은 쓰지 않는다.
- 푸시는 계획 4. 이 계획은 `MeetupCanceledEvent`, `MeetupApplicationPromotedEvent`만 발행한다 (트랜잭션 안에서 `ApplicationEventPublisher`로).

## Review Focus

1. **남은 자리 하나에 두 명이 동시에 신청** → 한 명만 확정, 다른 한 명은 대기 1번. 벙 행 잠금이 확정자 수 세기보다 먼저여야 한다. Task 3 테스트 `벙_잠금이_확정자_수_세기보다_먼저다`(InOrder).
2. **늦은 취소 경계** → 기준 시각 정확히에 취소하면 늦은 취소, 1초 전이면 아님. 기준 시각 이후 대기에서 자동 확정된 사람의 취소와 대기자의 취소는 표시하지 않는다. Task 3 테스트 `기준_시각_정각의_취소는_늦은_취소다`, `기준_시각_이후_자동_확정된_사람의_취소는_늦은_취소가_아니다`.
3. **명부 연결이 없는 ADMIN 계정** → 목록·상세는 `my: null`로 정상 응답, 신청은 403 `MEETUP_ROSTER_REQUIRED`. NPE가 나면 안 된다. Task 3 `명부가_없으면_403이다`, Task 4 `명부가_없는_운영진도_상세를_본다`.
4. **확정된 회원이 다가오는 벙을 남긴 채 탈퇴** → 그 신청은 취소(늦은 취소 아님)되고 대기 1번이 확정된다. 지난 벙의 참석 기록은 남는다. 계획 2의 탈퇴 리스너가 명부 연결을 끊기 전에 돌아야 한다. Task 3 테스트 `탈퇴하면_다가오는_벙_신청을_취소하고_대기자를_승격한다`, Task 6 통합 테스트.
5. **참석 보정을 노쇼↔참석으로 여러 번 바꿈** → 활성 노쇼 기록은 언제나 최대 하나, 되돌리면 취소된다. Task 5 테스트 `노쇼_참석_노쇼로_바꿔도_활성_노쇼는_하나다`.

## 이 계획이 끝나면 되는 것

- 운영진이 벙을 열고(복제 포함) 정원·명단 공개를 관리한다. 동호회원은 신청·대기·취소하고, 늦은 취소는 표시만 된다. 끝난 벙은 1분 안에 확정자 전원이 참석으로 기록되고, 운영진이 노쇼·불참으로 고치면 블랙리스트가 같이 움직인다.
- 계획 4가 이어받는 것: 참석률은 `attendances`(ATTENDED)와 `meetups`(취소 제외)로 SQL 집계한다. 푸시는 `MeetupCanceledEvent`·`MeetupApplicationPromotedEvent`를 구독하고, 이벤트의 명부 ID를 `RosterMember.getUser()`로 바꿔 보낸다 (연결 없으면 건너뜀).
- 정해 둔 것(스펙에 없던 결정): 동호회원 자격이 해제되면 다가오는 벙 신청을 취소하고 대기자를 승격한다 (2026-11-24 변경). 내보낸 사람은 같은 벙에 다시 신청할 수 없다. 벙 수정·내보내기는 시작 전까지, 벙 취소는 종료 전까지 가능하다. 벙 길이는 24시간 이하다.
- 아직 없는 것: 지난 기록 이관(`source = IMPORT`)은 3단계 또는 데이터를 받는 시점. 자동 기록 작업은 API 인스턴스가 하나라는 전제다 (여럿이 되면 ShedLock 등이 필요).
