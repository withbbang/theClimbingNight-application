# 2단계 좋아요·댓글 설계

작성 2026-11-27. 상위 설계는 `docs/superpowers/specs/2026-11-26-phase2-feed-design.md`(이하 "피드 설계")이고, 이 문서는 그 11장 2번 작업 중 **좋아요·댓글·대댓글**만 계획으로 옮길 수 있게 구체화한다. 피드 설계와 다르면 이 문서가 우선한다.

표기: **(결정)** 사용자가 정한 것, **(제안)** 설계자가 정한 것으로 사용자가 바꿀 수 있다.

## 1. 목적

피드 설계 1장 그대로: 동호회 사람들이 사진에 좋아요·댓글로 반응하는 SNS 피드. 1번 작업(사진 피드)으로 올리고 보는 것은 되지만, 반응할 방법이 없다. 이번 작업으로 반응을 붙인다.

성공: 회원이 안내 없이 좋아요·댓글·답글을 쓰고, 신고된 댓글을 운영진이 게시물처럼 숨길 수 있다.

실패로 볼 것(기술적으로 동작해도): 좋아요·댓글 수가 실제와 어긋나 쌓임 / 차단한 사람의 댓글이 보임 / 신고된 댓글을 운영진이 처리할 수 없음 / 비로그인 사용자가 댓글 내용을 받아 감.

## 2. 범위

### 하는 것

- 좋아요: 하트 버튼(켜고 끄기), 사진 두 번 탭(켜기만), 좋아요 누른 사람 목록.
- 댓글·대댓글(한 단계), 삭제, 신고, 운영진 숨김·복원·기각.
- 차단·탈퇴와 연동.

### 안 하는 것

- **프로필(3열 격자·프로필 사진)** — 별도 계획으로 뺀다 **(결정)**. 그 전까지 댓글·좋아요 목록의 아바타는 기본 이미지.
- 피드 카드의 댓글 미리 보기 — 수만 보인다 **(결정)**.
- 좋아요·댓글 푸시 알림 (피드 설계 2장 그대로).
- 댓글 수정, 댓글 좋아요, 댓글 고정, 멘션 자동완성, 작성 빈도 제한 (제안: 400~500명 규모라 필요해지면 추가).

## 3. 권한과 노출

피드 설계 3장 표를 따른다.

| 동작 | 비로그인 | USER 이상 | ADMIN |
|---|---|---|---|
| 좋아요 수·댓글 수 | O (볼 수 있는 게시물에서) | O | O |
| 좋아요 누른 사람 목록, 댓글·답글 목록 | X (401) | O | O |
| 좋아요, 댓글 작성, 댓글 신고 | X | O | O |
| 댓글 삭제 | X | 내 댓글 + 내 게시물에 달린 댓글 | 모두 |
| 댓글 숨김·복원(신고 목록에서) | X | X | O |

- **새로 쓰기**(좋아요 켜기, 댓글·답글 작성)는 `VISIBLE`인 게시물에만 된다. 아니면 404 (제안).
- **읽기**(댓글·답글·좋아요 목록)는 상세를 볼 수 있는 사람이면 된다. 상세 조회(`PostQueryService.detail`)와 같은 기준이라, 숨겨진 내 글의 작성자는 기존 댓글·좋아요를 볼 수 있다 (설계자 판단).
- **거두기**(좋아요 끄기, 댓글 삭제)는 게시물이 지워지지 않았으면 상태와 무관하게 된다. 숨겨진 글에서도 내 흔적은 지울 수 있게 한다 (설계자 판단).
- 앱 상세 화면은 `VISIBLE`이 아닌 글이면 댓글 입력창을 감추고 하트를 끈 상태로 보인다(이미 켠 좋아요는 끌 수 있음).
- 차단 관계(어느 쪽이든)인 사람의 게시물에는 좋아요·댓글을 할 수 없다. 상세 조회가 막히는 것과 같은 기준이다 (제안).
- 권한 검사는 모두 API에서 한다.

## 4. 좋아요 (결정)

- 하트 버튼은 누를 때마다 켜고 끈다. 사진 두 번 탭은 켜기만 한다(이미 켜져 있으면 하트 애니메이션만).
- 앱은 화면에 먼저 반영하고(낙관적 업데이트), 실패하면 되돌린다.
- API는 멱등: `PUT /api/v1/posts/{id}/like`(켜기), `DELETE /api/v1/posts/{id}/like`(끄기). 이미 그 상태여도 성공으로 응답한다. 응답은 최신 `likeCount`·`likedByMe` (제안).
- 피드 목록·상세 응답의 게시물에 `likedByMe`(boolean)를 추가한다. 비로그인이면 항상 false.
- 좋아요 누른 사람 목록: `GET /api/v1/posts/{id}/likes`, 최신순, 커서 페이징. 각 항목은 작성자 표시와 같은 모양(아이디·닉네임·아바타 자리). 차단 관계인 사람은 목록에서 뺀다. **숫자(`like_count`)는 차단과 무관한 전체 수** **(결정)**.
- 상세에서 "좋아요 n개"를 누르면 목록 화면으로 간다.

## 5. 댓글 (결정)

### 구조

- 댓글 1~500자. 앞뒤 공백을 자르고 비면 거절.
- 대댓글은 한 단계. 답글에 답하면 같은 부모(최상위 댓글) 아래 붙고, 답한 대상은 `reply_to_user_id`로 저장한다. 본문에 `@닉네임` 글자를 넣지 않고, 보여줄 때 지금 닉네임으로 `@닉네임`을 앞에 붙인다. 대상이 탈퇴했으면 "@알 수 없음".
- 최상위 댓글에 답하면 `reply_to_user_id`는 그 댓글 작성자.

### 보여 주기

- 순서: 최상위 댓글·답글 모두 오래된 순. 커서 페이징 20개씩.
- 답글은 접어 두고 "답글 n개 보기"를 누르면 불러온다 **(결정, A안)**. 최상위 댓글 응답에 `replyCount`를 넣는다.
- 엔드포인트(제안, 세부는 `api-conventions`를 따라 만드는 사람이 정함):
  - `GET /api/v1/posts/{id}/comments?cursor=` — 최상위 댓글
  - `GET /api/v1/comments/{id}/replies?cursor=` — 답글
  - `POST /api/v1/posts/{id}/comments` — `{ body, parentId? , replyToCommentId? }` 중 하나로 답글 대상을 받는다 (만드는 사람이 정함)
  - `DELETE /api/v1/comments/{id}`
- 각 댓글 응답: id, 작성자, 본문, 답글 대상 닉네임(답글만), 작성 시각, 상태(아래), 내가 지울 수 있는지(`deletable`), 내 댓글인지.
- 피드 카드는 댓글 수만 보인다. 카드의 댓글 버튼·"댓글 n개"를 누르면 상세로 가서 댓글 목록으로 바로 스크롤한다 **(결정)**.

### 삭제

- 작성자, 게시물 작성자, ADMIN이 지운다. 소프트 삭제(`deleted_at`).
- 보이는 답글이 남은 최상위 댓글을 지우면 자리에 "삭제된 댓글입니다"를 남긴다. 그 답글이 모두 지워지거나 숨겨지면 그 자리도 목록에서 빠진다.
- 게시물이 지워지면 댓글은 따로 지우지 않는다(게시물을 볼 수 없으니 댓글도 볼 수 없다) (제안).

### 숨김 상태 보이기

- 상태: `VISIBLE`, `HIDDEN_PENDING`(자동 숨김), `HIDDEN`(운영진 확정).
- 숨긴 댓글은 작성자 본인에게 "운영 정책에 따라 숨겨졌어요"로 보이고, 다른 사람에게는 안 보인다. 보이는 답글이 남은 최상위 댓글이면 "숨겨진 댓글입니다" 자리만 남긴다.
- 정리하면 최상위 댓글 자리 표시는: 보임 / 삭제 자리 / 숨김 자리 / 목록에서 뺌. 답글은 보임 / 목록에서 뺌(작성자 본인에게는 숨김 안내).

## 6. 신고·차단·운영진 조치

### 신고 (결정)

- 기존 `POST /api/v1/reports`에서 `targetType = COMMENT`를 연다(`ReportCreateRequest.isSupportedTarget` 제거).
- 사유는 게시물과 같되 `PORTRAIT_PRIVACY`(초상권)는 댓글에 쓸 수 없다(검증 오류). 앱 신고 시트도 댓글이면 그 항목을 뺀다.
- 서로 다른 3명이 신고하면 자동 숨김(`HIDDEN_PENDING`). 게시물과 같은 기준이며, 초상권 1건 규칙은 댓글에 없다.
- 신고가 들어오면 ADMIN 푸시(기존 `ReportSubmittedEvent` 재사용).
- 지운 댓글·숨긴 댓글을 신고할 수 있는지는 기존 게시물 신고(`ReportService`)와 같은 기준을 따른다.

### 운영진 조치 (결정)

- 기존 `POST /api/v1/report-targets/{targetType}/{targetId}/actions`에서 COMMENT의 숨김(HIDE)·복원(RESTORE)·기각(DISMISS)을 연다. 의미는 게시물과 같다:
  - HIDE → `HIDDEN`, 신고 ACTIONED
  - RESTORE → `VISIBLE`, 신고 DISMISSED
  - DISMISS → `HIDDEN_PENDING`이면 `VISIBLE`로 되돌림, `HIDDEN`은 그대로, 신고 DISMISSED
- 댓글은 미디어가 없으므로 격리·캐시 비우기 작업(`media_jobs`)을 만들지 않는다.
- 신고 목록(`GET /api/v1/report-targets`)의 COMMENT 항목에 댓글 본문, 작성자, 어느 게시물에 달렸는지(게시물 id, 가능하면 첫 사진 썸네일)를 보인다. 지운 댓글은 게시물처럼 기각만 보인다.
- 댓글이 달린 게시물이 **지워졌으면** 그 댓글은 지운 댓글처럼 기각만 된다. 게시물이 **숨겨졌으면** 댓글 숨김·복원·기각을 그대로 할 수 있다. 원 게시물 썸네일은 기존 신고 목록의 게시물 항목과 같은 방식으로 준다(숨긴 글이면 기존 격리본 처리 그대로) (설계자 판단).
- 앱 운영진 신고 목록(`ReportTargetRow`)에서 COMMENT 항목의 버튼을 API와 맞춘다.
- 상세 화면의 댓글 ⋯ 메뉴: 남의 댓글이면 신고·(그 사람)차단, 지울 수 있으면 삭제. ADMIN은 어떤 댓글이든 삭제할 수 있다. 숨김은 신고 목록에서만 한다 (제안: 게시물과 같음).

### 차단 (결정)

- 차단 관계(양방향)인 사람의 최상위 댓글·답글은 목록에서 뺀다. 차단 관계인 사람의 최상위 댓글에 달린 남의 답글도 함께 빠진다 (제안: 부모가 안 보이면 답글도 안 보임).
- `replyCount`·`comment_count`는 차단과 무관한 전체 수 **(결정)**. 그래서 "답글 3개 보기"를 눌렀는데 2개만 나올 수 있다(인스타그램과 같음).
- 운영진 신고 목록은 차단과 무관하게 모두 보인다(피드 설계 그대로).

## 7. 수 유지 **(결정, C안)**

- **좋아요 수**: 게시물 행을 먼저 `SELECT ... FOR UPDATE`로 잠근 뒤, `INSERT IGNORE`/`DELETE`의 영향받은 행 수가 1일 때만 같은 트랜잭션에서 `UPDATE posts SET like_count = like_count ± 1` **(결정)**. 처음에는 잠금 없이 하려 했으나, `post_likes → posts` 외래키 때문에 INSERT가 게시물 행에 공유 잠금을 걸고 이어지는 UPDATE가 배타 잠금으로 올리려다 동시 좋아요끼리 교착이 나서 바꿨다. 같은 글의 좋아요는 직렬로 처리되며 400~500명 규모에서 부담이 없다.
- **댓글 수**: 댓글이 바뀌는 모든 경우(작성·삭제·자동 숨김·운영진 숨김·복원·기각·탈퇴)에 게시물 행을 잠그고(`SELECT ... FOR UPDATE`) `comment_count`를 다시 센다. 세는 기준: 그 게시물의 `deleted_at IS NULL AND status = VISIBLE`인 댓글과 답글 전부(삭제·숨김 자리 표시는 세지 않음).
- 답글 수(`replyCount`)는 목록을 줄 때 같은 기준으로 센다 (제안: 컬럼 없이 묶어서 세기. 페이지당 20개라 부담이 작다. 만드는 사람이 비정규화가 필요하다고 판단하면 같은 방식으로 다시 세는 컬럼을 둬도 된다).
- 탈퇴처럼 여러 게시물에 걸친 정리는 영향받은 게시물마다 두 수를 모두 다시 센다(좋아요도 이때는 다시 센다).
- 잠금 순서: 게시물 행 → 댓글·좋아요 행. 좋아요·댓글 작성·삭제·운영진 조치·자동 숨김·탈퇴 모두 같은 순서를 지켜 교착을 피한다. 탈퇴처럼 게시물 여러 개를 잠글 때는 게시물 id 오름차순.
- 사용자 행이 게시물 행보다 먼저다: 좋아요·댓글 작성은 외래키로 참조할 사용자 행(본인, 답글이면 대상 작성자)을 id 오름차순 공유 잠금(`FOR SHARE`)한 뒤 게시물 행을 잠근다. 탈퇴(사용자 행 → 게시물 행)와 순서를 맞춰, INSERT의 외래키 공유 잠금 때문에 생기는 교착을 막는다.

## 8. 탈퇴 (피드 설계 7장 그대로)

- `UserWithdrawnEvent`에서 그 사람의 댓글·답글을 소프트 삭제하고 좋아요 행을 지운다. 영향받은 게시물마다 `like_count`·`comment_count`를 다시 센다.
- 그 사람이 단 최상위 댓글에 다른 사람의 보이는 답글이 있으면 "삭제된 댓글입니다"로 남는다(5장 삭제 규칙 그대로).
- 그 사람을 `reply_to_user_id`로 가리키는 답글은 "@알 수 없음"으로 보인다.
- 기존 `FeedWithdrawalListener`에 붙인다.

## 9. 데이터 모델 (Flyway V9)

```
comments    id, post_id → posts, author_id → users, parent_id → comments (nullable, 최상위면 NULL),
            reply_to_user_id → users (nullable), body VARCHAR(500),
            status(VISIBLE, HIDDEN_PENDING, HIDDEN), deleted_at, created_at, updated_at
            INDEX (post_id, parent_id, id)   -- 최상위·답글 목록 오래된 순 커서
            INDEX (author_id)                -- 탈퇴 정리
post_likes  post_id → posts, user_id → users, created_at
            PK (post_id, user_id)
            INDEX (post_id, created_at, user_id)   -- 누른 사람 목록 최신순 커서
            INDEX (user_id)                        -- 탈퇴 정리
```

- `posts.like_count`·`comment_count`는 V8에 이미 있다.
- 인덱스 세부는 만드는 사람이 정한다.

## 10. 앱 화면 (제안)

- **피드 카드**(`PostCard`): 하트(수), 말풍선(수). 사진 두 번 탭 하트 애니메이션, 하트 버튼 눌림 애니메이션(피드 설계 10장, 화면 작업 디자인 스킬 사용).
- **상세**(`posts/[id]`): 카드 + "좋아요 n개" + 댓글 목록 + 아래 고정 입력창. 답글 달기를 누르면 입력창 위에 "○○님에게 답글 ×". 키보드에 입력창이 가리지 않게.
- **좋아요 목록**(`posts/[id]/likes`): 아바타·닉네임 목록.
- **비로그인**: 상세에서 댓글 목록 자리에 로그인 안내, 하트를 누르면 로그인 안내.
- **운영진 신고 목록**: COMMENT 항목에 댓글 본문·작성자·원 게시물.
- 신고 시트(`ReportSheet`): 댓글이면 초상권 사유를 뺀다.

## 11. 문서 변경

- 피드 설계 11장: 2번을 "좋아요·댓글·대댓글(댓글 신고·숨김 포함)"으로 바꾸고, 프로필(격자·프로필 사진)을 별도 번호로 뺀다.
- `architecture.md` 10장 2단계 요약의 `comments, post_likes, profile_images` 줄을 나눠 반영.
- `docs/content-todo.md`: 개인정보처리방침에 댓글·좋아요 기록 보관(탈퇴 시 삭제) 확인 항목 추가가 필요하면 넣는다.
- 새 환경변수 없음.

## 12. 고려한 방식

**대댓글 보이기**: 접어 두기(채택) / 항상 펼치기. 후기 글에 대화가 몰려도 목록이 짧게 유지되도록 골랐다. 대가는 답글 API 하나 (사용자).

**피드 카드 댓글**: 수만(채택) / 최근 1~2개 미리 보기. 피드 응답을 가볍게, 카드 높이를 일정하게 두려고 골랐다. 댓글 버튼에서 상세 댓글로 바로 스크롤해 보완 (사용자).

**수 유지**: 모두 ±1 / 모두 다시 세기 / 좋아요 ±1 + 댓글 다시 세기(채택). 좋아요는 경우가 둘뿐이라 ±1, 댓글은 상태 전이가 많아 실수 여지가 없는 다시 세기 (사용자). 좋아요의 잠금은 외래키 교착 때문에 "게시물 행 먼저 잠금"(채택) / 잠금 없이 교착 시 재시도 중 앞의 것으로 정했다. 모든 경로가 게시물 행 → 하위 행 순서로 잠가 교착이 없다 (사용자).

**범위**: 좋아요·댓글만(채택) / 프로필까지. 프로필 사진은 워커 새 대상과 업로드 흐름이 따로라 겹치는 게 없어 계획을 나눴다 (사용자).

## 13. 만드는 사람에게 맡기는 것

- 엔드포인트 세부·응답 필드 이름(`api-conventions` 안에서), 답글 대상 지정 방식.
- 커서 인코딩(기존 `feed/Cursor` 재사용 여부), 페이지 크기 상한.
- 패키지 배치(`feed` 안 또는 `comment` 패키지).
- 앱 상태 관리 세부(기존 `use-post`·`use-feed` 캐시와 좋아요 낙관적 업데이트를 맞추는 방법).
- 화면 세부 디자인과 애니메이션.
